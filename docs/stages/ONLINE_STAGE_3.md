## Context
The online edition gets a customer website: customers browse the shop's products and place orders. The full plan:
- **Stage 3 (this one):** the backend for the website (public catalog API, customer accounts, placing an order) and the admin screens that control the website (website settings, delivery zones, which products show on the website).
- Stage 4: website orders in the admin app (statuses, stock reservation, turning an order into an invoice, notifications).
- Stage 5: the storefront app itself (a separate Angular app with SSR, `nota-storefront`), and moving the admin app to `/admin/`.
- Stage 6: the PWA.

So in this stage there is no storefront UI. Everything public is tested through the API.

## Decisions (already made; implement exactly)
1. **Same domain:** later the storefront is at `https://<domain>/` and the admin app at `https://<domain>/admin/`. The public API lives under `/api/store/`. Nothing in this stage moves the admin app.
2. **Payment:** cash on delivery only. `paymentMethod: "cod"` is the only value; keep it an enum so online payment can be added later.
3. **Customer accounts are optional:** a customer can order as a guest (name, phone, address) or with an account (register / sign in) and then see their own orders and saved addresses.
4. **Stock:** placing an order reserves and deducts nothing. Reservation happens when the shop confirms the order and the deduction when it becomes an invoice (both Stage 4). At placement the server only checks that each product is on the website, not archived, and that the quantity is ≤ the current `inventoryCount`.
5. **Delivery fee by zone:** the shop defines delivery zones, each with a fee, plus an optional "free delivery from order total X". The customer picks a zone. The zone fee is the **final amount the customer pays** for delivery; how it is split for VAT and accounting is decided in Stage 4.
6. **Reference only:** the old Kapomatic website is at `<KAPOMATIC_WEBSITE_PATH>`. You may read it for ideas (features, fields, flows). Do not copy its code; everything is written new on Nota's code and design.

## Hard rules
- **No change to existing business logic** (sales, credit, returns, purchases, inventory, cash boxes, shifts, accounting, VAT, reports). You may call existing pricing/VAT helpers read-only; do not change them. If one doesn't fit, say so in STEP 0.
- No refactoring or side improvements; list them at the end.
- **The public API never exposes internal data.** Every public response is built from an explicit whitelist of fields, never by returning a model with fields removed. Never: purchasePrice, wholesalePrice, profit, inventoryCount (exact), soldItemCount, lowStockThreshold, createdBy/updatedBy, audit data, codes of archived products, anything about users, customers (other than the signed-in one), suppliers, cash, accounting.
- **The server computes every price and total.** The client sends only product ids, quantities, the zone id and contact data. Prices, discounts, VAT, delivery fee and total are computed on the server from the database.

## Backend

### 1. Public API routing and security
- Mount the public router at `/api/store/`. Every route there is public for staff auth (it must not require the staff token) and is tagged so `test/permissions.test.js` still passes: propose in STEP 0 how (e.g. a `STORE` tag next to `PUBLIC`), and add every new route to `EXPECTED_ROUTES`.
- Customer accounts use **their own token**: a separate secret (`NOTA_STORE_JWT_SECRET`, required at start like `NOTA_JWT_SECRET`, generated by `setup-server.sh`) and a different audience. A customer token must be rejected by every staff route, and a staff token must be rejected by every customer route. Test both.
- If the website is disabled in settings (see 4), every `/api/store/*` route except `GET /api/store/settings` answers 503 `STORE_CLOSED`.

### 2. Product and category fields for the website
- Product: `website.visible` (bool, default **false**: nothing shows until the shop chooses), `website.description` (text, up to 2000 chars), `website.images` (up to 4 extra images, same base64 validation and size limit as the existing `image`).
- Category: `website.visible` (default false), `website.sortOrder` (number).
- A migration adds the fields with their defaults. Nothing is made visible automatically.
- Editing these fields needs the new `website.manage` permission (see 6), not `products.manage`.
- A product shows on the website only if: `website.visible`, not archived, its category exists and is `website.visible`.

### 3. Public catalog (`/api/store/`)
- `GET settings`: the public website settings (see 4) plus the shop name, logo URL, phones and address from ShopProfile.
- `GET categories`: visible categories (id, name, image URL, product count), sorted by `sortOrder` then name.
- `GET products?category=&q=&sort=&page=&limit=`: visible products. `sort`: newest, price-asc, price-desc, name. `q` searches the name. Paginated with the existing helper, `limit` at most 48.
- `GET products/:id`: one visible product. 404 for anything not visible (same answer as a missing id).
- Product fields: id, name, slug (from the name, Arabic allowed), category (id, name), price (retail), discountPercentage, finalPrice (after discount), VAT display as the shop's settings require (say in STEP 0 whether website prices are shown VAT-inclusive and how the existing helpers decide it), description, image URLs, `availability`: `in_stock` / `low` / `out_of_stock` (use the product's low-stock threshold; never the number), `maxOrderQty` = min(inventoryCount, 99).
- **Images:** never put base64 in catalog JSON. `GET /api/store/images/product/:id/:index` and `/category/:id` decode the stored base64 and answer the binary with the right Content-Type, a strong ETag and `Cache-Control: public, max-age=86400`; 304 on a matching If-None-Match; 404 for anything not visible. The image URLs in responses include a version (e.g. `?v=<updatedAt ms>`) so a changed image is fetched again.

### 4. Website settings (new model `WebsiteSettings`, single document like ShopProfile)
- `enabled` (website open), `orderingEnabled` (browsing only when false), `closedMessage`.
- `title`, `about` (text), `banners` (up to 5: base64 image, optional link to a category or product, sortOrder), `featuredCategoryIds` (up to 8).
- `whatsapp`, `facebook`, `instagram`, `tiktok` (URLs/numbers, validated).
- `minOrderAmount`, `freeDeliveryFrom` (optional, both ≥ 0).
- `orderNote` (shown at checkout, e.g. delivery times), `returnsPolicy`, `terms` (texts).
- Admin API: `GET/PUT /api/website/settings` (`website.manage`). Public: only the fields the storefront needs, through the whitelist.

### 5. Delivery zones (new model `DeliveryZone`)
- name, fee (≥ 0), `estimatedTime` (text, e.g. "خلال 24 ساعة"), `isActive`, `sortOrder`.
- Admin API `/api/website/delivery-zones` CRUD (`website.manage`). A zone used by any order can only be deactivated, not deleted.
- Public: `GET /api/store/delivery-zones` (active only: id, name, fee, estimatedTime).

### 6. Permissions
- New key `website.manage` (group "website", ar "إدارة الموقع", en "Manage website"). Role templates: owner (always), manager yes, others no.
- Placeholders for Stage 4 are NOT added now.
- Update the catalog labels, role templates, `EXPECTED_ROUTES` and the frontend permission list.

### 7. Customer accounts (new model `StoreCustomer`, separate from the shop's `Customer`)
- Fields: name, phone (unique, normalized: Egyptian mobile numbers, Arabic/Persian digits converted), bcrypt password, `addresses` (up to 5: label, zone, address text, notes), `isActive`, createdAt, lastLoginAt.
- `StoreCustomer` is **not** linked to the shop's `Customer` (the one used for credit sales). Linking happens in Stage 4 when staff confirm an order. Never look up or reveal a shop `Customer` from the public API.
- Routes: `POST auth/register`, `POST auth/login`, `GET me`, `PUT me` (name, password change with the current password), `GET/POST/PUT/DELETE me/addresses`, `GET me/orders`, `GET me/orders/:id` (only the customer's own orders).
- Login lockout per phone + IP, reusing the existing limiter.
- No SMS/OTP and no self-service password reset in this stage. Staff can reset a customer's password in Stage 4. The login page will say "forgot your password? contact the shop".

### 8. Placing an order (new model `WebOrder`)
- `POST /api/store/orders`, as a guest or with a customer token.
- Body: `items: [{ productId, qty }]` (1–50 lines, qty 1–99, no duplicate products), `zoneId`, `contact: { name, phone, address, notes }` (or `addressId` for a signed-in customer), `idempotencyKey` (UUID from the client).
- Server, in one transaction:
  - checks the website is open and ordering enabled;
  - checks every product (visible, not archived, qty ≤ inventoryCount) and the zone (active); on any problem answers 409 with a per-line list (`not_available`, `quantity_exceeds_stock` with the current max, `price_changed` is not needed because the client never sends prices);
  - prices every line with the same helpers a cash sale uses (retail price, product discount, VAT per the shop's settings), computes subtotal, VAT, delivery fee (0 when `freeDeliveryFrom` is set and reached), total;
  - checks `minOrderAmount` against the subtotal;
  - creates the order with a number from the existing document-number helper (prefix proposed in STEP 0, e.g. `W-`).
- **Idempotency:** the same `idempotencyKey` returns the same order (no second order). Unique index.
- Stored order (snapshot, never recalculated later): number, status, `source: "website"`, `paymentMethod: "cod"`, items (productId, name, code, unitPrice, discount, VAT, qty, lineTotal), subtotal, vat, deliveryFee, total, zone (id, name, fee), contact (name, phone, address, notes), storeCustomer (optional), statusHistory `[{ status, at, by }]`, createdAt.
- Status enum now: `new`, `confirmed`, `preparing`, `out_for_delivery`, `delivered`, `cancelled`, `rejected`. In this stage only `new` is created and the customer can cancel their own order while it is `new` (`POST me/orders/:id/cancel`). All other transitions are Stage 4.
- Response: order number, status, totals, and a public `trackingToken` (random) so a guest can see the order at `GET /api/store/orders/track/:token` (status, items, totals, zone; no other data).

### 9. Admin API for orders (read only in this stage)
- None. Orders are managed in Stage 4.
